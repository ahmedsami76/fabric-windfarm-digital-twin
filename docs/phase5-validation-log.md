## Lessons

- A client that is only built has not been checked. The part that fails is the one that runs last: the connection, and whatever it loads on the way. Open it, even to an address where nothing listens.
- The words "checked against the library" need the verb that was checked. I wrote them for a constructor.
- Measure what an action does before writing the message that proposes it. The curtailment I was about to put on an approval card changed nothing at the wind I was about to show it in (finding 10).
- A fallback value that names a real thing is a command waiting for a caller that forgets. `WT-07` as the notebook's own turbine was harmless while a person filled the cell in (finding 13).
- Before describing a page from guesses, look for the form the product publishes of the thing behind the page. The agent's definition and its API were there (finding 16).
- When two pages of the same documentation disagree on a name, depend on neither (finding 17).
- A documented "typically" is the good case. When a time matters, quote the slow case the same page gives, and measure before answering a review that names a number (finding 24).
- A property I claim for a thing has to hold for every way the thing can be made. "The action cannot stop a turbine" was true of the payload my script wrote and false for the action the portal builds from the same notebook (finding 26).
- A stand-in built from a page proves that I read the page. The page said the playbook is an empty placeholder; the service returns it full and checks it. The first call against the real thing told more than twenty tests (obstacles B and C).
- Ask the service for a round trip before building on it: read, write back unchanged. Ten seconds, and it would have shown this on the first evening of Phase 3.
- A hint that names a step of a guide is a link, and links are checked. Mine was a number in a string (obstacle B).
- Before building what a plan says, ask for each item who knows the fact. "The agent confirms" and "who approved" were both written by someone who had not asked (finding 29).
- Write a rule twice when it cannot be run: once where it has to live, once where it can be tested. The Python copy of the KQL function found a limit that would never end (finding 31). It proves the rule, not the KQL, and the guide has to say which.
- A check that passes is as good as what it reads. Grammar passed for a year of KQL files; the first function that compares columns needed a check that knows the columns (finding 33).
- A test that asserts only the result cannot tell two ways of getting it apart. False for "refused" and False for "timed out" (finding 36). Plant the fault and see.
- A picture is a claim. The first one of the limit showed a limit that held nothing down, and a time that was wrong by two minutes (findings 39 and 40). Read it as the audience will.
- The status line of a README is the most-read sentence of a delivery and the last one I look at (finding 44).
- When a thing is changed to suit a new user of it, ask what becomes of the old one. I made notebook 12 safe for the agent and said in one line that it still works by hand; that it had become awkward by hand, the user had to tell me (finding 23).
